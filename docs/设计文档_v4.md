# DeepLister 设计文档 v4

> 会追问的AI调研Agent — 基于Harness架构的对话式调研方案预研

---

## 1. 产品定义

### 1.1 一句话描述

DeepLister是一个在问卷执行中动态追问的AI调研Agent，帮助用户更准确地表达主观感受，提升数据画像质量。

### 1.2 核心命题

| | 效率 | 深度 | 可纠偏 | 可迭代 |
|---|---|---|---|---|
| 静态问卷 | ✅ | ❌ | ❌ | ❌ |
| 人工访谈 | ❌ | ✅ | ✅ | ❌ |
| **DeepLister** | **✅** | **✅** | **✅** | **✅** |

实现路径的关键认知：**不要只把AI项目理解成"模型+prompt+对话界面"，而要把它理解成一套围绕模型运转的工作系统。** 追问不是模型自由发挥的产物，而是Harness系统在每一步决策中引导模型输出的结果。

### 1.3 场景：心理测评

**选择理由：** 主观感受密集，理解偏差是核心痛点，追问价值最直观；全年龄段覆盖，认知水平差异大，是Agent适应不同用户的天然试验场。

**定位边界：** DeepLister帮助用户更准确地表达主观感受，不做心理诊断。诊断结论由专业医生做出。

### 1.4 与Dots Life Agent的关联

Dots要解决：Agent如何在模糊需求中理解用户，形成长期memory和personalization。

DeepLister要解决：AI如何在主观表达场景中检测理解偏差、挖掘真实意图、积累用户画像。

两者面对同一个本质挑战——**用户说的不等于用户想的，Agent需要"听懂"而非仅仅"听到"。**

本项目以**Harness**为核心架构关键词，以**Memory**为产品能力关键词，自然对标Dots的技术方向。

## 2. 工作原理与流程总览

### 2.1 DeepLister是什么

一句话：DeepLister是一个会追问的AI调研员。它把传统问卷变成对话，在用户回答后自动判断"需不需要追问"和"怎么追问"，帮用户把模糊的主观感受说清楚。

### 2.2 三方协作模型

```
研究者（上传问卷，配置参数）
    ↓
DeepLister引擎（拆解话题，驱动对话，记录决策）
    ↓
受访者（自然对话，无需理解问卷结构）
```

- **研究者**：定义"我想了解什么"（上传问卷 + 设定追问深度）
- **受访者**：只需要自然对话，不需要看题、读题、理解题
- **DeepLister引擎**：在两者之间做翻译和深挖——把研究者的问题翻译成受访者能理解的表达，把受访者的回答深挖出研究者需要的信息

### 2.3 端到端流程

```
┌──────────────────────────────────────────────────────────┐
│ 第一阶段：调研发起（研究者操作，一次性完成）               │
│                                                          │
│  上传问卷JSON → 引擎解析为话题序列 → 研究者确认/调整      │
│  设定追问深度（轻度/中度/深度）                           │
└────────────────────────┬─────────────────────────────────┘
                         ↓
┌──────────────────────────────────────────────────────────┐
│ 第二阶段：对话执行（受访者与引擎交互，核心环节）           │
│                                                          │
│  话题1                                                   │
│  ├── 引擎发出开场问题                                     │
│  ├── 受访者回复                                          │
│  ├── 引擎四步编排：检测→仲裁→生成→校验                    │
│  │   ├── 有信号触发？→ 生成追问（回到受访者回复）          │
│  │   └── 无信号/达到上限？→ 推进下一子问题或完成话题       │
│  ├── ...重复直到话题1的所有核心维度被覆盖                  │
│  └── 话题1完成，过渡到话题2                               │
│                                                          │
│  话题2 ... 话题N                                         │
│  └── 同上流程                                            │
└────────────────────────┬─────────────────────────────────┘
                         ↓
┌──────────────────────────────────────────────────────────┐
│ 第三阶段：结果输出                                        │
│                                                          │
│  单用户结构化画像 → 决策日志（每轮追问的完整判断过程）      │
└──────────────────────────────────────────────────────────┘
```

### 2.4 核心循环：每轮对话的四步编排

这是DeepLister的灵魂。用户每说一句话，引擎不是直接回复，而是走四步：

```
用户说了一句话
    ↓
Step 1 检测：这句话有没有"问题"？
    ├── 理解偏差（用户没听懂/回答含糊）
    ├── 信息不足（只有结论没有原因）
    ├── 前后矛盾（和之前说的不一致）
    └── 安全信号（自伤/崩溃倾向）
    ↓
Step 2 仲裁：如果有问题，该怎么处理？
    ├── 优先级排序（安全>理解>矛盾>信息不足）
    └── 纯代码规则，不走AI，保证确定性
    ↓
Step 3 生成：按仲裁策略生成追问
    ├── 每种策略有对应的生成指令
    └── 追问不超过2句话，语气自然不带审讯感
    ↓
Step 4 校验：生成的追问质量过关吗？
    ├── 策略一致？没重复？不超长？安全？
    └── 不通过则修正，通过才输出给用户
```

**如果四步都走完没有触发追问（无信号），就直接推进到下一个子问题或下一个话题。**

### 2.5 一次完整对话示例

**场景：SCL-90心理健康测评精简版，话题"睡眠质量"**

| 轮次 | 角色 | 内容 | 引擎内部发生了什么 |
|---|---|---|---|
| 1 | 引擎 | "最近一周睡眠怎么样？有没有入睡困难或者早醒的情况？" | 开场问题，来自问卷JSON |
| 2 | 用户 | "还行吧" | 检测：理解偏差（回答含糊）→ 仲裁：理解纠偏 → 生成：降维提问 → 校验：通过 |
| 3 | 引擎 | "用1到10打分的话，大概在哪个位置？" | 追问第1轮 |
| 4 | 用户 | "4分吧，不太容易睡着" | 检测：信息不足（无原因）→ 仲裁：深度挖掘 → 生成：追问原因 → 校验：通过 |
| 5 | 引擎 | "是什么让你不容易睡着？是脑子里想事情，还是身体不舒服？" | 追问第2轮 |
| 6 | 用户 | "主要是想事情，工作上压力比较大" | 检测：无信号 → 仲裁：推进 → 下一子问题 |
| 7 | 引擎 | "明白了。白天会觉得精力不够吗？" | 推进到子问题2 |
| ... | ... | ... | ... |
| N | 引擎 | "睡眠这块我了解了，接下来聊聊情绪方面，可以吗？" | 话题完成，过渡到话题2 |

### 2.6 这和"让AI自由追问"有什么不同

| | 让AI自由追问 | DeepLister的四步编排 |
|---|---|---|
| 什么时候追问 | 模型自己决定 | 检测层判断，仲裁层选策略 |
| 怎么追问 | 模型自己发挥 | 生成层按策略模板生成 |
| 追问质量 | 不可控 | 校验层把关，不通过就修正 |
| 追问太多 | 可能无限追问 | 仲裁层硬上限3轮 |
| 追问重复 | 可能反复问 | 校验层检测重复，强制换角度 |
| 出错了怎么修 | 重新生成 | 定位问题、局部修正 |
| 能不能迭代 | 无法积累经验 | 每轮决策链路完整记录，数据闭环 |

**一句话总结区别：** 不是"让AI自由追问"，而是"用一套系统让AI的追问可控、可检查、可修正、可迭代"。

## 3. 为什么用Harness而非Prompt工程

### 3.1 三个阶段的认知演进

| 阶段 | 核心问题 | 代表方案 | 局限 |
|---|---|---|---|
| 提示词工程 | 怎么写prompt让模型按要求输出 | 精心设计的prompt模板 | 单次生成不可控，长链路必然偏移 |
| 上下文工程 | 怎么让模型在正确时机拿到正确信息 | RAG、知识库、Skill | 信息有了，但决策流程仍是黑盒 |
| **Harness工程** | **怎么让模型在复杂任务中持续做对** | **信息边界+执行编排+评估校验+数据闭环** | **设计复杂度高，但这是AI产品真正该做的事** |

### 3.2 如果只用Prompt思维设计DeepLister

```
用户回复 → 一个大prompt → 模型自由决定要不要追问、怎么追问 → 输出
```

问题：
- 模型什么时候该追问？不知道，靠"感觉"
- 追问质量怎么验证？没有机制
- 追问错了怎么修正？整段重来
- 多次对话之间怎么积累？没有状态管理
- 能不能根据数据持续优化？没有数据回流

**这就是"做了一个对话机器人"和"设计了一个AI产品系统"的区别。**

### 3.3 用Harness思维重新设计

```
用户回复 → [信息边界] 加载当前话题的最小必要上下文
         → [执行编排] 分步执行：检测→仲裁→生成→校验
         → [评估观测] 追问质量实时打分
         → [约束校验] 不合格则修正，非推翻重来
         → [记忆更新] 结构化信号写入画像
         → [数据回流] 决策日志沉淀，驱动后续迭代
```

每一步都不是模型"自由发挥"，而是系统在引导模型做对的事。

## 4. Harness架构·六大组件

### 组件一：信息边界（Information Boundary）

**原则：模型不应该每次读取全部资料，而是只调用当前任务最相关的信息。**

| 决策时刻 | 模型需要的信息 | 不需要的信息 |
|---|---|---|
| 判断用户是否理解题意 | 当前问题文本 + 用户回复 + 用户认知水平 | 其他话题的对话记录 |
| 判断信息是否充分 | 当前话题的核心维度定义 + 用户已回答内容 | 已完成话题的详细记录 |
| 判断前后是否一致 | 当前话题内的关键信号 + 一致性标记 | 未触发一致性问题的历史记录 |
| 生成追问 | 仲裁策略 + 当前话题上下文 + 用户沟通偏好 | 之前话题的追问历史 |
| 话题过渡 | 当前话题摘要 + 下一话题开场问题 | 已完成话题的完整对话 |

**实现方式**：不是把全部对话历史塞进prompt，而是从记忆层按需加载。

```python
def load_context(task: str, topic_id: str, user_profile: dict) -> dict:
    """根据当前任务类型，加载最小必要上下文"""
    base = {
        "current_topic": user_profile["topics_status"][topic_id],
        "cognitive_level": user_profile["cognitive_level"],
        "communication_preference": user_profile["communication_preference"],
    }
    
    if task == "comprehension_check":
        base["current_question"] = get_current_question(topic_id)
        base["user_reply"] = get_latest_reply()
    
    elif task == "consistency_check":
        base["key_signals"] = get_topic_signals(topic_id)
        base["consistency_flags"] = get_unresolved_flags(topic_id)
    
    elif task == "follow_up_generate":
        base["arbitration_result"] = get_arbitration_result()
        base["topic_context"] = get_topic_context(topic_id)
    
    return base
```

**为什么要这么做**：
- 减少token消耗，降低API成本
- 避免信息过载导致模型判断泛化
- 让每个决策环节的输入可控、可审计

### 组件二：执行编排（Execution Orchestration）

**原则：任务不能一上来就直接生成最终答案，而是要拆成判断、检索、分析、生成、检查等步骤。**

追问不是一次生成，而是四步编排：

```
Step 1: 信号检测（Detect）
    输入：用户回复 + 最小上下文
    输出：结构化检测结果JSON
    模型职责：只做判断，不做生成

Step 2: 策略仲裁（Arbitrate）
    输入：检测结果
    输出：响应策略
    职责：纯规则代码，不走LLM，保证确定性

Step 3: 回复生成（Generate）
    输入：策略指令 + 话题上下文 + 用户画像
    输出：自然语言回复
    模型职责：只做生成，不做判断

Step 4: 质量校验（Verify）
    输入：生成的回复 + 原始策略指令
    输出：通过/不通过 + 修正方向
    模型职责：只做检查，不做生成
```

**为什么拆成四步而不是一个大prompt**：
- 检测和生成是不同任务，混在一起检测不准、生成不自然
- 仲裁层用代码保证优先级逻辑100%确定性执行
- 校验层是最后一道关：追问是否真的在执行策略？有没有跑偏？
- 每步可独立调试，哪步出了问题改哪步

#### Step 1: 信号检测

并行检测四类信号，输出结构化结果：

```json
{
  "safety": {
    "triggered": false,
    "type": null,
    "confidence": 0.02
  },
  "comprehension": {
    "triggered": true,
    "type": "vague_reply",
    "detail": "回复过短且含糊：'还行'",
    "confidence": 0.85
  },
  "consistency": {
    "triggered": false,
    "type": null,
    "confidence": 0.10
  },
  "sufficiency": {
    "triggered": true,
    "type": "conclusion_without_reason",
    "detail": "只有状态描述无归因：'最近心情不好'",
    "confidence": 0.78
  }
}
```

#### Step 2: 策略仲裁

纯规则，不走LLM：

| 优先级 | 信号 | 策略 | 附加约束 |
|---|---|---|---|
| P0 | safety.triggered=true | `safety_protocol` | 立即中断追问流程 |
| P1 | comprehension.triggered=true | `comprehension_correction` | 换表述+给具体参照 |
| P2 | consistency.triggered=true | `consistency_confirmation` | 引用前文，确认矛盾 |
| P3 | sufficiency.triggered=true | `depth_mining` | 追问场景/原因/影响 |
| P4 | 无信号触发 | `proceed` | 推进下一子问题或话题 |

多信号触发时，只执行最高优先级策略，不叠加追问。

附加规则：
- 单话题追问累计≤3轮 → 强制推进
- 连续2次敷衍回复 → `skip_topic`
- 用户主动跳过 → `skip_topic`
- 追问轮次=0且无信号 → `transition`（话题完成，过渡到下一话题）

#### Step 3: 回复生成

根据策略生成自然语言，每条策略有对应的生成指令模板：

| 策略 | 生成指令核心 |
|---|---|
| `comprehension_correction` | 用通俗表述替换原题抽象词汇，给出具体频率/程度参照，请用户举最近一次的例子 |
| `consistency_confirmation` | 引用用户前文原话，指出当前回答的差异，询问是情境不同还是理解变化 |
| `depth_mining` | 针对缺失维度追问：无原因→追问场景，频率模糊→追问具体次数，程度模糊→追问影响范围 |
| `proceed` | 确认用户回答后推进下一子问题 |
| `transition` | 承接上文结论+预告下文方向，以开放式问题开启新话题 |
| `skip_topic` | 简短确认后推进，不强行追问 |
| `safety_protocol` | 关怀话术+专业求助资源，不追问 |

**生成约束**：
- 追问不超过2句话
- 不重复用户已表达的内容
- 语气保持自然、不带审讯感
- 基于用户认知水平调整用词（画像中cognitive_level驱动）

#### Step 4: 质量校验

生成后立即校验，不走LLM无法保证：

| 校验项 | 判断标准 | 不通过时 |
|---|---|---|
| 策略一致性 | 生成内容是否在执行仲裁策略 | 重新生成，最多重试1次 |
| 重复检测 | 是否与最近2轮追问语义重复 | 重新生成，更换追问角度 |
| 长度约束 | 追问是否≤2句话 | 截断至2句 |
| 安全性 | 追问是否可能引发用户不适 | 降级为proceed策略 |

**校验通过后才输出给用户，不通过则修正后再输出。** 这是Harness和Prompt工程的关键区别：不是生成完就结束，而是生成后有验收机制。

---

### 组件三：记忆状态（Memory & State）

**原则：画像不是事后产物，是对话过程中持续写入、持续驱动的活数据。**

#### 记忆分层

```
[工作记忆] 当前对话的即时上下文（最近3轮）
    ↓ 话题完成时提炼
[用户画像] 跨次持久化的结构化数据
    ↓ 会话开始时加载
[对话状态] 未完成话题、中断位置、待追问项
```

#### 画像结构

```json
{
  "user_id": "xxx",
  "cognitive_level": "medium",
  "communication_preference": "prefer_concrete_examples",
  "topics_status": {
    "sleep_quality": {
      "status": "completed",
      "core_dimensions_covered": ["difficulty", "duration", "impact"],
      "key_signals": ["入睡困难持续2周+", "影响白天工作"],
      "follow_up_count": 2,
      "completeness_score": 0.85
    },
    "anxiety": {
      "status": "in_progress",
      "current_sub_question": "anxiety_triggers",
      "key_signals": ["工作场景触发焦虑"],
      "follow_up_count": 1
    }
  },
  "consistency_flags": [
    {
      "topic_pair": ["sleep_quality", "anxiety"],
      "description": "睡眠问题严重但焦虑评分偏低",
      "resolved": false
    }
  ],
  "session_history": [
    {
      "date": "2026-01-15",
      "topics_completed": ["sleep_quality"],
      "duration_minutes": 12
    }
  ]
}
```

#### 画像更新时机

| 时机 | 写入内容 | 读取方 |
|---|---|---|
| 信号检测后 | 检测到的信号、认知水平调整 | 仲裁层、生成层 |
| 话题完成后 | 话题状态、核心维度覆盖、完成度评分 | 下次会话恢复 |
| 一致性问题 | 跨话题一致性标记 | 检测层、生成层 |
| 会话结束时 | 会话记录、未完成话题 | 下次会话恢复 |

#### 画像如何驱动决策

| 画像字段 | 驱动哪个环节 | 怎么驱动 |
|---|---|---|
| cognitive_level | 生成层 | 决定追问用抽象表述还是具体例子 |
| communication_preference | 生成层 | 决定追问策略：偏好举例→场景式，偏好概括→范围式 |
| consistency_flags | 检测层 | 跨话题矛盾检测的输入 |
| completeness_score | 仲裁层 | 话题完成判定的依据 |
| follow_up_count | 仲裁层 | 追问上限控制 |

**这不是"存着好看"的画像，是每一轮对话都在读写的工作数据。**

---

### 组件四：评估观测（Evaluation & Observation）

**原则：系统要有标准判断模型做得好不好。不是事后看指标，是运行时实时评估。**

#### 运行时评估（每轮对话自动执行）

| 评估项 | 采集方式 | 判断标准 | 触发动作 |
|---|---|---|---|
| 追问有效性 | 下一轮用户回复的信息量 | 回复信息量>追问前 | 有效，记录策略+效果 |
| 追问冗余度 | 与前2轮追问的语义相似度 | 相似度<0.7 | 合格 |
| 用户疲劳度 | 连续回复的长度趋势 | 长度持续递减>3轮 | 降低追问频率 |
| 话题完成质量 | 核心维度覆盖率 | ≥2/3维度有信息 | 允许推进 |

#### 事后评估（每次会话结束后）

| 评估项 | 采集方式 | 用途 |
|---|---|---|
| 完成率 | 完成话题数/总话题数 | 整体效果衡量 |
| 信息丰富度 | 每话题关键信号数 vs 静态问卷 | 追问价值量化 |
| 追问触发分布 | 各策略类型的触发比例 | 调优仲裁规则 |
| 安全信号召回 | 安全事件是否被正确检测 | 安全校验底线 |

#### 对照实验设计

同一问卷，5人用DeepLister版，5人用静态问卷版：
- **主指标**：每个话题提取的关键信号数（信息丰富度）
- **副指标**：完成率、完成时间、用户满意度
- **不求统计显著性**，求方向性验证

---

### 组件五：约束校验（Constraint & Correction）

**原则：如果检查出问题，模型要能定位问题，并在可控范围内修正，而不是整篇推翻重写。**

#### 运行时约束

| 约束 | 机制 | 违反时动作 |
|---|---|---|
| 追问轮次上限 | 仲裁层代码计数 | 达3轮强制推进 |
| 追问不重复 | 质量校验层语义比对 | 重新生成，换角度 |
| 追问不超过2句 | 质量校验层字数检查 | 截断 |
| 不偏离策略 | 质量校验层一致性检查 | 重新生成 |
| 安全兜底 | P0优先级+安全协议 | 中断追问，展示求助资源 |

#### 修正机制：局部修正而非全盘重来

```
质量校验不通过
    ↓
[定位问题] 是哪条校验项不通过？
    ↓
[判断可修正性] 
    策略不一致 → 重新生成（保留策略，换表述）
    语义重复 → 重新生成（换追问角度）
    超长 → 截断
    安全风险 → 降级为proceed
    ↓
[重试] 最多1次
    ↓
仍不通过 → 降级为proceed（放弃追问，推进话题）
```

**关键：不推翻重来，而是定位问题、局部修正。** 这比"生成不好就重新生成"高效得多，也是Harness思维的核心体现。

---

### 组件六：数据闭环（Data Flywheel）

**原则：一个可迭代的AI项目，不只是当下能跑通，而是能在使用中不断积累经验。**

#### 采集什么数据

```json
{
  "session_id": "xxx",
  "turns": [
    {
      "turn_id": 1,
      "user_reply": "最近心情不太好",
      "detection_result": { "sufficiency": {"triggered": true, "type": "conclusion_without_reason"} },
      "arbitration_result": { "strategy": "depth_mining", "priority": "P3" },
      "generated_reply": "最近有什么具体的事情让你心情不好吗？",
      "verification_result": { "passed": true },
      "next_user_reply": "工作压力特别大，天天加班",
      "evaluation": { "follow_up_effective": true, "information_gain": "high" }
    }
  ]
}
```

每一轮都完整记录：用户输入→检测结果→仲裁策略→生成回复→校验结果→用户下一轮反馈→效果评估。

#### 数据怎么回流

```
[采集] 每轮对话的完整决策链路
    ↓
[标注] 追问是否有效（基于下一轮用户回复的信息量自动判定）
    ↓
[分析] 哪些策略在哪些场景下效果好/差
    ↓
[迭代] 调整检测prompt / 仲裁规则 / 生成模板
    ↓
[验证] 下一轮5人内测对比
```

**这是数据飞轮的最小闭环**——不是等大量数据才转，而是5个人测完就能转第一圈。

#### 未来升级路径

| 当前 | 升级方向 | 条件 |
|---|---|---|
| Prompt检测 | 微调小模型做信号检测 | 积累200+标注样本 |
| 规则仲裁 | 学习型仲裁（根据历史效果调整优先级权重） | 积累500+决策记录 |
| Prompt生成 | 微调生成模型 | 积累1000+有效追问样本 |
| JSON文件存储 | 向量数据库+语义检索 | 数据量超过单机承载 |

## 5. 完整决策流（端到端示例）

```
用户回复："还行吧，也不太好说"
    ↓
[信息边界] 加载：当前问题文本 + 用户认知水平 + 当前话题状态
    ↓
[Step1 检测]
    输出：comprehension=vague_reply(0.82), sufficiency=conclusion_without_reason(0.75)
    ↓
[Step2 仲裁]
    comprehension优先级P1 > sufficiency优先级P3
    策略：comprehension_correction
    追问轮次+1（当前第2轮，未超限）
    ↓
[Step3 生成]
    指令：降维提问，给具体参照
    生成："用1-10打分的话，大概在哪个位置？是什么让您给这个分？"
    ↓
[Step4 校验]
    策略一致性：✅  重复检测：✅  长度约束：✅  安全性：✅
    ↓
[输出给用户]
    ↓
[记忆更新] 更新认知水平评估：偏好具体参照式提问
    ↓
[数据回流] 记录完整决策链路，标注待验证
```

## 6. 竞品差异（Harness视角）

| 维度 | 传统问卷 | AI问卷产品 | DeepLister |
|---|---|---|---|
| 信息边界 | 无（用户自己看题） | 无（全量context） | **按决策时刻动态加载最小必要信息** |
| 执行编排 | 无（静态题面） | 单prompt端到端 | **检测→仲裁→生成→校验，四步编排** |
| 评估观测 | 无 | 无 | **每轮追问有效性+疲劳度实时评估** |
| 约束校验 | 无 | 无 | **质量校验层+局部修正机制** |
| 记忆状态 | 无 | 无 | **持续读写的工作画像，驱动每轮决策** |
| 数据闭环 | 无 | 无 | **完整决策链路沉淀，驱动迭代** |

**核心差异**：现有AI问卷产品在"生成问卷"环节做文章，DeepLister在"执行问卷"环节做文章；且不是简单地"让AI追问"，而是**用Harness系统让追问变得可控、可检查、可修正、可迭代**。

## 7. 可行性评估

### 7.1 项目发起人条件

| 维度 | 现状 | 影响 |
|---|---|---|
| 专业背景 | 大三数学系，非CS | 有逻辑思维和抽象建模能力，但工程经验有限 |
| AI编程工具 | $20 Codex | 可辅助代码生成，但预算紧张，需精打细算 |
| 展示平台 | GitHub | 开源+文档展示，不依赖付费云服务 |
| 开发经验 | Vibe Coding个人网站、简历工具 | 有AI辅助开发经验，但无后端服务开发经验 |

### 7.2 技术可行性判断

| 模块 | 技术难度 | 是否依赖工程经验 | Codex/ChatGPT可帮多少 | 可行性 |
|---|---|---|---|---|
| 问卷解析（纯Python逻辑） | 低 | 否 | 高 | ✅ |
| 检测层prompt（核心能力） | 中 | 否 | 高 | ✅ |
| 仲裁层代码（纯规则） | 低 | 否 | 高 | ✅ |
| 生成层prompt（核心能力） | 中 | 否 | 高 | ✅ |
| 校验层prompt | 中 | 否 | 高 | ✅ |
| Harness编排器（四步串联） | **高** | 是 | 中 | 🟡 |
| 记忆层（数据持久化） | 中 | 是 | 中 | ✅ |
| Web前端 | **高** | 是 | 中 | 🔴 |
| 实时对话通信 | **高** | 是 | 低 | 🔴 |
| 部署运维 | 中 | 是 | 中 | 🟡 |

**结论：核心引擎（1-5）完全可行，是纯prompt+规则逻辑，Codex可以高质量生成。但包装成完整Web产品（7-10）的工程复杂度超出了当前条件的舒适区。**

### 7.3 技术选型决策过程

**前端框架选型：**

| 方案 | 优势 | 劣势 | 适合场景 |
|---|---|---|---|
| React + Vite | 生产级，生态成熟 | 需前端经验，开发周期长 | 专业团队长期维护 |
| Gradio | Python原生，上手快 | UI不够灵活，对话体验差 | 快速原型展示 |
| **Streamlit** | **纯Python，对话组件现成** | **非生产级，定制受限** | **个人项目MVP** |

**选择Streamlit，理由：**
1. 纯Python，不需要学任何前端知识
2. `st.chat_message` + `st.chat_input` 对话UI开箱即用
3. 研究者端和受访者端可在同一Python进程内实现
4. Streamlit Cloud免费部署，面试官点链接即可体验
5. **核心目标是验证Harness引擎的有效性，不是构建生产级Web服务。用最小技术成本把核心体验做透，比用复杂架构做出半成品更有价值。**

**LLM选型：**

| 方案 | 优势 | 劣势 | 适合场景 |
|---|---|---|---|
| OpenAI GPT-4o | 能力最强 | 贵，$20预算不够 | 追求质量 |
| **OpenAI GPT-4o-mini** | **便宜，中文够用** | **复杂推理偶有偏差** | **MVP验证** |
| 本地Ollama（Qwen等） | 免费 | 依赖本地算力 | 开发调试期省钱 |
| DeepSeek API | 性价比高 | 偶有服务不稳定 | 备选 |

**选择GPT-4o-mini + 开发期Ollama，理由：**
1. 4o-mini单次调用成本约$0.00015，$20预算可支撑数千次调用
2. 开发调试阶段用Ollama本地模型，不消耗API预算
3. 检测层和校验层对推理精度要求不极端，4o-mini足够

**为什么不用LangChain：**
- Harness的四步编排是自定义流程，LangChain的Agent/Chain抽象无法直接表达
- 减少依赖=减少不确定性，面试时能说清每一步做了什么
- LangChain的抽象层增加了调试难度，对非CS背景不友好

**为什么不用RAG：**
- 心理测评场景下，AI需要的是当前话题的结构化定义（核心维度、子问题），不是大规模非结构化知识检索
- 信息边界设计已经解决了"模型需要什么信息"的问题，RAG的检索-增强范式在此场景下是过度设计
- 上一版昌荣项目的教训：RAG在查询模式固定的场景下引入的噪音和维护成本大于收益

| 阶段 | 工具 | 用途 |

| 方案设计 | 本文档 | 指导所有后续开发 |

## 8. 风险与降级策略

### 8.1 技术风险

| 风险 | 概率 | 影响 | 降级策略 |
|---|---|---|---|
| 检测层prompt准确率不够，漏检/误检频繁 | 高 | 中 | ① 降低追问深度为"轻度"（仅理解纠偏），先保证P1信号准确；② 人工review决策日志，补标注数据；③ 积累数据后微调小模型替代prompt |
| 仲裁规则覆盖不了新信号（如反讽、方言） | 中 | 低 | ① 新信号出现时归入P4（无信号→推进），不追问比乱追问好；② 发现新信号后手动添加规则，仲裁层代码天然支持扩展 |
| 生成层追问语气不自然/审讯感 | 中 | 高 | ① 校验层增加"语气自然度"检查项；② 生成prompt增加few-shot示例；③ 仍不通过时降级为proceed |
| 校验层过于严格导致频繁重试 | 低 | 中 | ① 重试上限1次，不无限循环；② 仍不通过直接降级proceed；③ 放宽校验标准（MVP阶段容忍轻微偏差） |
| GPT-4o-mini上下文理解不足 | 低 | 中 | 关键场景（一致性检测）切GPT-4o，牺牲成本换质量 |

### 8.2 产品风险

| 风险 | 概率 | 影响 | 降级策略 |
|---|---|---|---|
| 用户不按预期对话（恶意输入、极度沉默） | 中 | 低 | ① 敷衍检测→跳过话题；② 恶意输入→安全协议兜底；③ 整体设计原则：**不追问比乱追问好** |
| 追问反而增加用户压力，导致完成率低于静态问卷 | 中 | 高 | ① 追问深度可配置，降低为"轻度"；② 追问不超过2句+3轮上限已经是最严约束；③ 如果实验验证追问确实降低完成率，说明核心假设不成立，这是有价值的发现 |
| 画像数据积累不足，跨次记忆无法形成有效驱动 | 高（MVP阶段） | 中 | ① MVP先做单次对话，不依赖跨次记忆；② 画像在单次对话内的实时驱动已可验证Harness价值 |

### 8.3 伦理风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 用户在对话中表达自伤倾向，AI未检测到 | 严重 | P0安全信号检测+安全协议，宁可误报不可漏报 |
| 开源项目被用于非专业心理评估场景 | 中 | README明确声明"本工具不用于心理诊断"，定位为数据采集辅助 |
| 对话数据隐私 | 中 | 画像只存结构化信号不存原文，开源Demo只用模拟数据 |

## 9. 产品功能·MVP

### 9.1 做

**研究者端（Streamlit页面）**
1. 上传问卷（JSON格式）
2. AI拆解话题序列，研究者审核/调整
3. 配置追问深度（轻度/中度/深度）
4. 查看单用户画像+决策日志

**受访者端（Streamlit对话页面）**
1. 进入对话界面
2. 追问引擎驱动对话，四步编排每轮执行
3. 全部话题完成后对话结束

**结果端**
1. 单用户结构化画像（JSON）
2. 决策日志回放（展示Harness每一步的判断过程——**Demo核心亮点**）

### 9.2 不做（MVP阶段）

- 快捷模式（AI自动生成问卷）
- 跨次对话记忆（次级目标，核心目标验证后再做）
- 跨用户聚类分析
- 可视化看板
- 多语言/方言适配

### 9.3 分步实现策略

**核心目标（先做）：** 单次对话内的完整追问引擎
- 四步编排：检测→仲裁→生成→校验
- 画像实时更新驱动决策
- 研究者端+受访者端最小闭环

**次级目标（后做）：** 跨次对话的长期记忆
- 会话恢复+画像持久化
- 认知水平跨次积累
- 一致性检测范围扩大至跨话题

### 14.2 方案价值判断

**值得做的理由：**
1. 从真实观察出发（医院场景），不是拍脑袋的伪需求
